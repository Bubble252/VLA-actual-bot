## 1. 三句话结论

1. **挂载点**在远端 `FlowmatchingActionHead.predict_action` 的 Euler `for t in range(num_steps)` 内，在算出 `pred_velocity` 之后、`actions = actions + dt * pred_velocity` 之前（或把该更新包进 guidance）。  
2. **prefix 必须在归一化空间**与 DiT 一致；client 若持有物理 ΔEEF，需先 `apply` 进 norm，或由 server 用同一套 `PolicyNormProcessor` 规范化后再 guidance。  
3. StarVLA 积分方向是 **t: 0→1**（与 EVO1 同类），**不能**原样套 Pi0 的 `euler_integrate`（t: 1→0）；若复用 LeRobot `RTCProcessor`，需按 EVO1 方式做时间/速度符号映射。

## 2. LeRobot `RTCProcessor.denoise_step`（对照）

文件：`LEROBOT/lerobot-main/src/lerobot/policies/rtc/modeling_rtc.py`

| 项 | 内容 |
|----|------|
| 输入 | `x_t` 当前轨迹；`prev_chunk_left_over` leftover；`inference_delay`；`time`；原速度函数 |
| prefix 权重 | `get_prefix_weights(delay, execution_horizon, T)`：前 `delay` 步权重 1；`delay→horizon` 线性/指数衰减；其后 0 |
| 干净估计 | 在 Pi0 约定下用 `x1_t = x_t - time * v_t`（processor 内部还做 `tau = 1 - time`） |
| guidance | `err = (prefix - x1_t) * weights`；对 `x_t` 反传得 `correction`；`v' = v - guidance_weight * correction` |
| 无 prefix | 直接返回原 `v_t` |

Pi0 官方环（`common/flow_matching.py`）：

```text
time: 1 → 0
dt = -1/N
x <- x + dt * v
RTC: 直接 denoise_step(..., time=time, original=v)
```

EVO1 / **与 StarVLA 同类**（`evo1/flow_matching.py` 注释）：

```text
t: 0 → 1
dt = +1/N
x <- x + dt * v    # v ≈ x1 - x0
复用 RTCProcessor 时：
  time_arg = 1 - t
  guided = denoise_step(..., time=time_arg, original=lambda x: -v(x))
  velocity = -guided
```

**对本仓**：优先采用与 EVO1 相同的适配；或手写一份「0→1 约定」的 guidance，避免符号搞反。

## 3. StarVLA 挂载点（改这里）

### 3.1 主插入点（必须改）

| # | 文件（远端 `/root/code/Starvla`） | 函数 | 行号（2026-08-08） | 改什么 |

| 2 | 同上 Euler 环 | `for t in range(num_steps):` 内 | ~577–615 | **插入点**：`pred_velocity = pred[:, -action_horizon:]` 之后；`actions = actions + dt * pred_velocity` 之前 |

现网环（简化）：

```text
actions ~ N(0,I)          # shape (B, 8, 7)，归一化空间
for t in 0..N-1:          # N = num_inference_timesteps
    t_cont = t / N        # 0 → (N-1)/N
    pred_velocity = DiT(...)

return actions            # normalized
```

建议改成：

```text
v = DiT(...)
if rtc_enabled and prefix is not None:
    v = rtc_guide(actions, v, prefix, delay, horizon, t_cont, dim_mask)
actions = actions + dt * v
```

## 5. 归一化侧对齐（leftover 用哪一侧）

调用链：

```text
DiT Euler  →  normalized_actions (B,T,7)
PolicyServerWrapper  →  proc.unapply_actions → 物理 actions 给 client
```

| 量 | 空间 | 说明 |
|----|------|------|
| Euler 中的 `actions` / `pred_velocity` | **normalized** | guidance 必须在此空间 |
| `prev_chunk_left_over` 送进 DiT | **normalized** | 与 `x_t` 同空间、同 shape 可 pad 到 (B,8,7) |
| client 正在执行的 leftover | 通常是 **物理 ΔEEF** | 需 `apply`（unnorm 的逆）后再当 prefix；或 server 收物理量后内部 normalize |
| 夹爪 | 可仍走 unnorm 后的命令语义 | 但 **不参与** prefix guidance |

**推荐约定（供 P2 写死）：**

- 请求字段 `rtc_prefix`：**normalized**，shape `(T_left, 7)` 或 `(T_left, 6)`（若只传 pose，server pad gripper=0 且 mask 掉）；  
- 若 client 只方便持有物理量：增加 `rtc_prefix_space=physical|normalized`，server 用同一 `unnorm_key=franka` 的 stats 转换。

## 6. Chunk / 步数对超参的约束

现网 eef ckpt（5694/5695）配置：

| 参数 | 值 | 对 RTC 的约束 |
|------|-----|----------------|
| `action_horizon` / chunk `T` | **8** | `execution_horizon ≤ 8`；且 ≤ leftover 长度 |
| `num_inference_timesteps` `N` | **4** | guidance 每步都算（含 autograd）→ 相对现网最多约数倍算力，需测延迟 |
| `inference_delay` | 整数步 | 必须 `0 ≤ delay ≤ T`；且 ≤ 当前 leftover 长度 |
| `execution_horizon` | 建议起步 **4～6** | 论文/LeRobot 默认 10，但本仓 T=8，**默认不要 >8**；可先试 `4` |
| `max_guidance_weight` | LeRobot 默认 10 | 先沿用，数值不稳再降 |
| 控制频率 | 真机常见 20–30 Hz | delay 步 ≈ `ceil(infer_latency * hz)`；chunk 短，异步窗口很紧 |

`RTCProcessor` 已有保护：`execution_horizon > leftover_len` 时会截断到 leftover 长度。

## 8. 风险备忘（P1 发现）

1. **时间约定搞反**会导致越 guidance 越偏；必须以 EVO1 注释或单元数值对照验证。  
2. **T=8 很短**：delay 稍大就会吃掉几乎整个 chunk，RTC 收益变小——client 侧 delay 估计要保守。  
3. **autograd**：serving 默认 `eval()` + 可能 bf16；guidance 段需 `torch.enable_grad()`，并确认 bf16 下 correction 稳定。  
4. **相对 ΔEEF**：leftover 是「旧 chunk 未执行的 Δ 序列」，不是绝对 pose；不要做绝对 pose 的 reanchor（LeRobot `relative.py` 那套仅在 relative-to-state 动作时需要）。
