> 文档位置：`RTC/DOC/`  
> 关联仓库：`ARX_X5_clean_server46(7.12get-data)`  
> 参考实现：`LEROBOT/lerobot-main/src/lerobot/policies/rtc/`  
> 工程近似参考：`arx_example/arx5-sdk-main/simulation/doc/04_smoothing_strategy.md`、`参考平滑方法/`  
> 状态：**需求起草（2026-08-08）**

---

## 1. 要解决什么问题

Physical Intelligence 的 **Real-Time Chunking（RTC）** 解决的是：VLA / flow policy 推理有延迟时，机器人不能停下来等模型；常见 action chunking 在新旧 chunk 边界会产生位置、速度、加速度不连续。

本仓当前真机部署链路是：

```text
本机 ARX client
  -> websocket 请求远端 Policy Server
  -> StarVLA 返回一段 action chunk
  -> 本机逐步执行（关节 / 末端→IK）
```

希望把 RTC（或其可落地的子集）接到这条链路上，使：

1. **异步推理**：执行旧 chunk 的同时后台请求新 chunk；  
2. **边界连续**：新 chunk 到达后不硬切，而是与旧 chunk 未执行部分对齐；  
3. **可复用、可对照**：既能对照 LeRobot 官方 RTC 源码，又能服务 ARX + StarVLA 现有工程，而不是另起一套无法上真机的 demo。

## 3. 现状（2026-08-08 已核实）

### 3.1 远端 Policy Server（`ssh -p 27219 root@115.190.90.101`）

正在运行的是 **StarVLA / QwenGR00T**，不是 LeRobot Pi0：

| 端口 | 权重要点 | 动作空间 |
|------|----------|----------|
| **5794** | `arx_x5_joint_clean` / `steps_15000` | `action.joints` + gripper |
| 5695 | scratch / `steps_7750` | 末端 pose + gripper（`franka` 归一化） |
| 5694 | full / `steps_98000` | 同上 |

架构要点：

- 骨干：**SpikeBrain VLM**；  
- 动作头：**GR00T 风格 Flow-matching DiT**（推理侧 Euler 积分，`num_inference_timesteps` 约 4）；  
- 对外接口：`predict_action` → **只返回最终 action chunk**（常见 `action_chunk_size=8`）；  
- 客户端 **拿不到** denoise / Euler 中间状态，也 **插不进** LeRobot `RTCProcessor`。

### 3.2 LeRobot RTC 模块（本仓已有源码树）

路径：`LEROBOT/lerobot-main/src/lerobot/policies/rtc/`

- 它是 **推理增强**，不是独立策略；  
- 官方对接：**Pi0 / Pi0.5 / SmolVLA** 等 flow-matching action expert；  
- 核心在 denoise 每一步做 **prefix guidance**，并配合 `ActionQueue` 管理 leftover / delay。

### 3.3 本仓已有工程近似

`04_smoothing_strategy.md` 已明确：若只有最终 pose/joint chunk，只能做 **后处理 soft overlap + 关节平滑限幅**，不能复现论文级 guided inference。  
`参考平滑方法/rtc_demo/` 已有确定性 stitching 演示，可作对照基线。

## 4. “完整 RTC” vs “本仓可立刻用的 RTC”

| 对比项 | 完整 RTC（论文 / LeRobot） | 本仓短期可落地 |
|--------|----------------------------|----------------|
| 作用位置 | flow/diffusion **生成过程内部** | chunk **输出之后** 的拼接 / 平滑 |
| 需要访问 | `v_π`、中间轨迹 `A_τ`、VJP / guidance | 旧 leftover + 新 chunk + delay |
| 与当前 StarVLA server | **不兼容开箱**（需改服务端采样循环） | **兼容**（client 或中间层即可） |
| 与 ARX 机器人 | 不绑定机型；绑定的是策略生成方式 | 可接关节 chunk 或末端 chunk→IK |

结论：

1. **机器人本身可以用 RTC 思想**（异步执行 + overlap 约束）。  
2. **当前远端模型类型“沾边”**（flow-matching DiT），但 **部署接口不符合直接挂 LeRobot RTC 的条件**。  
3. 因此本项目分两轨：  
   - **轨 A（工程 RTC）**：先在 client / 平滑层落地 soft overlap，服务现网 StarVLA；  
   - **轨 B（完整 RTC）**：评估并可选地在 StarVLA `FlowmatchingActionHead.predict_action` Euler 环内移植 guidance。

---

## 5. 成功标准（验收口径）

1. 文档把两轨边界写清楚，团队不会误以为“装了 LeRobot 就等于真机 RTC”。  
2. 有一条可运行的 **轨 A** 通路：对合成或录制 chunk，边界加速度 / 跳变指标优于 naive 硬切（对照 `rtc_demo` 指标思路）。  
3. 对远端 StarVLA 给出明确结论表：哪些端口 / 权重属哪类动作空间；轨 B 若要做，改动点落在服务端哪几个函数。  
4. 真机接入必须显式开关 + 安全门控；默认 dry-run / 仿真。
