## 1. 要解决什么问题

在 ARX X5 用策略 client 真机跑的时候，终端只有数字日志，现场很难直觉看到：

1. **基座坐标系**朝哪；  
2. **末端坐标系**相对基座的姿态；  
3. **采集 HDF5 里同一时刻/同类约定下的轴**长什么样（从数据还原，不是口头定义）；  
4. **双相机图像**当前看到什么。

本工具目标：在跑 `eval_starvla_libero_x5.py`（经 `run_local_client.sh`）时，**边执行边可视化**；回放（teleop `r/p/v`）只预留接口，不作为第一期交付。

| 项 | 决定 |
|----|------|

## 3. URDF/MuJoCo FK 在本工具里到底干什么？（已对齐理解）

### 3.1 你的意图（合理，且作为主需求）

闭环里常见链路是：

```text
策略 / IK  →  解出关节目标角 q_cmd  →  mode=5 发给真机
```

你想用 MuJoCo + URDF 做的是：**把这组关节角再正算一遍**，在 3D 里完整看到「按模型，末端应该在哪、轴朝哪」——  
即 **关节目标角 → FK → 末端位姿的复现**，不是为了另搞一套「官方末端定义」。

这完全合理：尤其 2p（EEF→IK→关节）时，能直接检查「解出来的 `q` 对应的末端」是否还停在怪地方 / 和策略想要的 EEF 是否对得上。

实现上优先驱动：

1. **`q_cmd`（本步下发的关节目标）** → MuJoCo FK → 末端轴（主）；  
2. 若暂无 `q_cmd`，退化为当前反馈 **`joint_pos`** → 同理画「当前构型下的模型末端」。

### 3.2 SDK `/arm_status.end_pos` 是什么（次要、可选）

- 控制器报告的「真机当前末端」（实测/SDK 内部解算）。  
- 采集 HDF5 的 `observations/eef` 通常来自这条。  
- **用途**：旁边看一眼「胳膊实际报到哪」；**不是**本工具用 MuJoCo 的首要目的。  
- 已知 SDK 与 URDF 绝对数值常对不齐——同显时务必标清图例，但 **不要理解成「必须做双源对账产品」**。

### 3.3 本期约定（按你的理解改写）

| 优先级 | 内容 |
|--------|------|
| 主 | MuJoCo 加载 URDF，用 **关节目标角（优先）/ 当前关节** 驱动，显示整臂 + **模型 FK 末端轴** |
| 次 | 可选叠加 SDK `end_pos` 轴，便于和真机反馈对照 |
| 不 | 用可视化去「校正」控制器或强行统一两套数值 |

## 4. 系统背景（摘要）

```text
笔记本: eval_starvla_libero_x5.py
  ├─ 读相机 + /arm_status
  ├─ WebSocket → Policy Server
  ├─ mode=5 发 /arm_cmd
  └─（本期）旁路/hook → Play Viz（MuJoCo 窗口）
```

- 策略在 GPU；感知与执行在本机。  
- 闭环默认：`action_repeat=2`，多用 chunk 的 `action[0]`。

---

## 5. 采集轴「从 HDF5 还原」含义

- 指定一条（或默认最近）采集 episode：`*.hdf5`。  
- 读取其中的 `observations/eef`、`observations/qpos`、以及 `cam_high` / `cam_wrist`（若有）。  
- 在 MuJoCo 场景中：  
  - 可用 **半透明/异色** 机器人或仅坐标轴，表示「采集时某一帧」；  
  - 或固定显示「参考帧」轴 + 当前真机轴，便于对比定义是否一致。  
- 具体选帧策略（首帧 / 与当前 step 对齐 / 用户指定 index）在实现计划 P4 细化。

## 7. 成功标准

1. 跑策略 client 时，MuJoCo 可见：**基座轴、由关节目标角 FK 复现的末端轴、整臂 URDF**；SDK `end_pos` 可选同显。  
2. 能从指定 HDF5 还原并显示 **采集参考轴（及可选参考图像）**。  
3. 可见双相机（或至少腕部）实时/近实时图像。  
4. 可视化异常不导致控臂失控；不需要截图导出功能。  
5. 预留 `ReplaySource` 类接口，供日后 `r/p/v` 接入，第一期不实现回放 UI。
